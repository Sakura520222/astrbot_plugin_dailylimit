## 1. 审查质量评估

### 覆盖度

本次审查准确抓住了变更的核心问题：`ConfigLoader` 将配置写入插件实例，而 `Limiter` 从 `config_mgr` 读取，导致配置来源不一致。针对变更涉及的 5 类配置项逐一核对，覆盖了本次 diff 的主要语义影响。

不过，审查仍有以下覆盖不足：

- **未充分验证插件属性的初始化与生命周期**
  - 需要确认 `self.plugin.skip_patterns`、`group_modes`、`time_period_limits`、`user_limits`、`group_limits` 在所有初始化路径上都已存在。
  - 如果某些配置加载失败、插件尚未完成初始化，直接访问 `self.plugin.*` 可能引入 `AttributeError`。
- **未验证配置更新的原子性和并发安全**
  - WebUI 热加载可能与消息处理并发执行。若 `ConfigLoader` 是逐个替换属性，`Limiter` 可能在更新过程中读取到不一致的一组配置。
- **未核对默认值和空值行为**
  - 特定用户/群组配置为空、配置格式异常、限制为 `0` 或负数时，`get_user_limit()` 是否仍能正确回退到全局限制，审查摘要没有给出结论。
- **未验证配置键类型的一致性**
  - 群号、用户 ID 在配置文件中可能是字符串，而运行时上下文可能使用整数。切换数据源后，键匹配是否一致仍应通过测试确认。
- **未实际展示测试证据**
  - PR 描述列出了功能测试计划，但审查结果只提到“已核对”和 `ruff check`，没有说明功能测试、热加载测试是否实际执行。

因此，静态一致性检查较完整，但运行时行为验证不足。

### 准确度

`approve` 和 9/10 的总体判断基本合理，原因是：

- 修改范围小，仅涉及单文件和配置读取位置；
- 改动与当前 `ConfigLoader` 的写入位置一致；
- 未发现明显的逻辑反转、类型错误或无关改动；
- 该修复确实能解决“特定用户/群组限制永远不生效”的核心问题。

但评分略偏乐观。若没有实际功能测试，建议评分更接近 **8/10**，或在批准时明确附带验证要求。尤其是：

- “关键配置均已由 `ConfigLoader` 写入 `plugin`”只能证明静态写入位置一致；
- 不能单凭此确认所有构造路径、热加载路径和异常配置路径都安全；
- PR 描述中提到的“critical”影响较大，但审查没有验证修复前后行为差异。

`self.config_mgr` 在构造函数中保留但未使用，当前确实更像代码清理项，而不是本 PR 的阻塞缺陷。将其标记为 follow-up 是合理的。

### 完整性

对变更意图的理解是正确的：这是一次数据源统一，而不是限流规则本身的重写。

但审查还可以补充确认：

1. `Limiter` 是否应完全依赖 `plugin`，还是仍有部分全局配置必须从 `config_mgr` 读取；
2. `plugin` 是否一定是当前实例，而非共享或代理对象；
3. 所有调用 `Limiter` 的入口是否都在插件初始化完成后执行；
4. `ConfigLoader` 的后续重构是否可能再次改变配置归属，是否需要统一封装访问接口以避免重复出现此类问题。

## 2. 发现的模式

### 代码模式

- 项目当前存在“配置加载对象”和“配置消费对象”分离的模式：
  - `ConfigLoader` 负责加载；
  - `plugin` 保存配置；
  - `Limiter` 消费配置。
- 该模式下容易出现“写入 A、读取 B”的隐性回归，尤其是在模块化重构后通过属性转移实现兼容时。
- `Limiter` 通过直接访问多个 `plugin.*` 属性获取配置，耦合了插件实例的数据结构。
- 构造函数中仍保留 `self.config_mgr`，说明旧依赖尚未完全清理，存在架构迁移未收尾的迹象。

### 架构观察

- 项目采用插件实例级配置，支持多插件实例或独立插件配置，这是合理的隔离设计。
- `ConfigManager` 与插件实例之间的职责边界目前不够清晰：
  - 如果配置属于插件实例，应统一由插件或专门的配置对象持有；
  - 如果配置属于全局，应继续由 `ConfigManager` 管理；
  - 当前两者混用容易造成来源漂移。
- WebUI 热加载链路依赖对象属性被原地更新，因此配置对象的所有权和更新语义非常重要。
- 当前依赖图过于简化，只显示 `core/limiter.py`，没有体现 `ConfigLoader`、插件实例和 WebUI 热加载之间的真实数据流。对配置类问题而言，这会降低审查辅助信息的价值。

## 3. 规范完善建议

建议新增以下审查规则：

1. **配置写入/读取一致性规则**
   - 对每个配置字段追踪完整数据流：定义、初始化、加载、热更新、消费。
   - 检查写入对象与读取对象是否一致，不能只检查字段名称一致。

2. **插件实例隔离规则**
   - 插件级配置不得从全局单例或共享管理器读取，除非明确标注为全局配置。
   - 多插件实例场景应至少有一个隔离性测试。

3. **初始化安全规则**
   - 插件属性应在构造阶段统一初始化默认值；
   - 消费方不应假设配置加载一定成功；
   - 必要时使用显式默认值或配置对象，而不是裸属性访问。

4. **热加载一致性规则**
   - 配置热更新应尽量整体替换配置快照，而不是逐字段更新；
   - 需要检查消息处理线程/协程与配置更新之间是否存在竞态。

5. **配置键与边界值规则**
   - 明确用户 ID、群组 ID 的类型转换策略；
   - 明确 `0`、负数、空配置、非法值和缺失值的语义；
   - 为默认回退逻辑补充测试。

6. **废弃依赖清理规则**
   - 当数据源迁移完成后，检查旧依赖字段、构造参数和导入是否仍然必要；
   - 对暂时保留的兼容代码添加注释或后续清理任务。

项目特有规范可以明确为：

> 所有由 `ConfigLoader` 加载的插件级配置，必须通过插件实例或统一的插件配置对象访问；禁止在业务模块中混用 `ConfigManager` 和插件属性作为同一配置的来源。

## 4. 经验教训

- 配置来源错位是静态检查中很容易漏掉、但运行时影响很大的问题。审查时应优先建立“谁写入、谁持有、谁读取、何时更新”的数据流图。
- 小 diff 不代表低风险。此次只有 12 行修改，但直接影响限流策略，可能导致所有用户或群组绕过定制限制。
- 对这类修复，最有价值的验证不是 lint，而是行为测试：
  - 特定群组限制是否生效；
  - 特定用户限制是否生效；
  - 无匹配配置时是否回退默认值；
  - 热加载后是否立即生效；
  - 插件实例之间是否互不影响。
- 代码审查应区分“静态证据”和“运行时证据”。本次静态结论充分，但运行时证据不足，未来不宜仅凭字段归属一致就给出接近满分的评价。
- 更长期的改进方向是引入统一的配置快照或配置对象，让 `Limiter` 依赖明确接口，而不是直接依赖插件实例的多个公开属性，从根本上减少再次出现数据源漂移的可能。
